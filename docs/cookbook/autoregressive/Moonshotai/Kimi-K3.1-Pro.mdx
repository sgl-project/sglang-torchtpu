## Overview

**Kimi K3.1 Pro** ([`moonshotai/Kimi-K3.1-Pro`](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)) is Kimi-K3 with a DSA sparse indexer (top-2048) on each of its 24 MLA
layers. On TPU it runs on the same 2x2x4 slice as Kimi-K3 ([Kimi-K3 TPU deployment](/cookbook/autoregressive/Moonshotai/Kimi-K3#tpu)): 16 tpu7x chips on
four hosts (4 chips x 2 TensorCores each), one engine, tp32/ep8. The MoE weights
stay in the checkpoint's MXFP4 and the MLA KV cache is fp8 (`fp8_e4m3`).
Validated with `torch_tpu` 0.2.0 and `libtpu` 0.0.50.

<Note>
**Highlights** (93 layers, 16 tpu7x chips, one request unless stated):
- **~133 tok/s** decode at 8K context and **~112 tok/s at 128K**: decode speed holds across the context window.
- **~530 tok/s** with the decode megakernel + DFlash on GSM8K (experimental, section 4), and **~700 tok/s** at an acceptance length of 6.
- **5.1 s** TTFT for a 128K prompt with a 90% prefix-cache hit; **~11K tok/s** (input + output) at 128K with 2 concurrent sessions.
- Accuracy: **AIME25 30/30**, **MATH-500 98.4%**, **GPQA-diamond 93.4%**, **HumanEval 98.2%**, needle-in-a-haystack **100%** up to 128K.
</Note>

**Docker image:** `lmsysorg/sglang:dev-kimi-k31-pro-tpu` (SGLang with the TPU
plugin, `torch_tpu` and `libtpu` preinstalled). Pull it on all four hosts and run
the commands below inside it, with host networking and access to the TPU devices:

```bash
docker pull lmsysorg/sglang:dev-kimi-k31-pro-tpu
docker run -it --privileged --net=host --ipc=host \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    lmsysorg/sglang:dev-kimi-k31-pro-tpu bash
```

The commands load `moonshotai/Kimi-K3.1-Pro` from Hugging Face, so the first
start on each host downloads about 1.5 TB of weights into the mounted cache. To
avoid the wait, download them on every host beforehand (also the DFlash draft
if you use section 2):

```bash
huggingface-cli download moonshotai/Kimi-K3.1-Pro
huggingface-cli download RadixArk/Kimi-K3.1-Dflash2-Preview   # only for section 2
```

As for Kimi-K3, every host runs the same command, adding its own
`--node-rank <0-3> --dist-init-addr <node0-ip>:20000`. With the recipe launcher
(`python3 -m benchmark.tpu.launch_server`), the node rank and the rank-0
address come from `TPU_WORKER_ID` and `TPU_WORKER_HOSTNAMES` instead.

## 1. Native server (128K context)

The Kimi-K3 TPU server plus the K3.1 sparse-MLA backend, fp8 KV, radix cache,
the per-op decode flags, four host-side decode launch switches
(`SGLANG_TPU_DECODE_SKIP_GUARD_EVAL`, `SGLANG_TPU_AOT_LEAN_RUNTIME_WRAPPER`,
`SGLANG_TPU_SPLIT_EXEC_DIRECT_CALL`, `SGLANG_TPU_PALLAS_VMEM_RIGHTSIZE`; validated
on K3.1 only, so the K3 commands leave them off) and the DSA indexer token split, sized for a 128K
context (131072 in + 8192 out) and up to 64 running requests. Prefill is
chunked at 4096 tokens, the one compiled EXTEND bucket, and a chunk carries up
to 8 requests. 256K (262144) context has also been tested.

The command is generated from `benchmark/tpu/recipe/configs/kimi_k3_1/server.py`
(change the recipe, not the page).

What the K3.1-specific settings do (each `SGLANG_TPU_*` switch is off by
default; the Kimi-K3 ones are described in [Kimi-K3 TPU deployment](/cookbook/autoregressive/Moonshotai/Kimi-K3#tpu)):

| Setting | Effect |
| --- | --- |
| `--attention-backend pallas_tpu_mla_sparse` | Sparse MLA with the DSA indexer on the 24 indexed layers. |
| `--kv-cache-dtype fp8_e4m3` | fp8 MLA KV cache. |
| `--max-total-tokens 4000000` | An upper bound only: the pool is sized by `--mem-fraction-static`, about 532K tokens on 16 chips. MLA KV and DSA index keys are replicated on every rank. |
| `SGLANG_TPU_ENABLE_QBLOCK_SPARSE_MLA_PREFILL` | Query-blocked sparse MLA prefill for the DSA layers. |
| `SGLANG_TPU_VL_TEXT_ONLY_EXTEND` | Compiles only the token-id prefill graphs (text serving), which saves host memory at startup. |
| `SGLANG_TPU_TWOLEVEL_ALLREDUCE_SPLIT_BARRIER`, `SGLANG_TPU_K3_QKVG_PREFETCH`, `SGLANG_TPU_K3_LATENT_UP_ATTN_RES`, `SGLANG_TPU_K3_OPROJ_ROW` | Per-op decode kernels (all-reduce barrier split, KDA qkvg weight prefetch, attention residual fused into latent-up, row-split o_proj). |
| `SGLANG_TPU_DYNAMO_PARAMS_AS_GRAPH_ATTRS=2`, `SGLANG_TPU_ALLOC_DECODE_FAST_PATH` | Cut host overhead per decode step; at batch 1 decode on 93 layers is host bound. |
| `SGLANG_TPU_LOGITS_ONESHOT_GATHER` | One-shot Pallas all-gather of the decode logits. |
| `xla_tpu_offload_gather_to_sparsecore=true` | Runs the DSA top-k gathers on the SparseCore. |
| `xla_tpu_buffer_assignment_enable_fast_merge_fallback=false` | Needed with large KV pools on libtpu before 0.0.51. |

## 2. Optional: DFlash speculative decoding (one request)

On top of section 1, with the Kimi-K3.1 DFlash draft
[`RadixArk/Kimi-K3.1-Dflash2-Preview`](https://huggingface.co/RadixArk/Kimi-K3.1-Dflash2-Preview)
(8 tokens per verify: 7 proposals plus the anchor), for single-stream latency:
**5.34 ms TPOT (~187 tok/s)** at 8K, with a mean accept length of 4.0. It serves
one request at a time (`--max-running-requests 1`); requests that ask for
logprobs are answered with a 400.

The draft model uses MLA; the server expands its latent and serves it as
multi-head attention, so the draft attention backend is `pallas_tpu_rpa_v3`.

For long-context (64K-128K) serving, the native server (section 1) is recommended.

```bash
export SGLANG_TPU_ENABLE_EXPERIMENTAL_SPEC_WORKER=1
export SGLANG_RAGGED_VERIFY_MODE=static
export SGLANG_SPEC_TP_SYNC=rng
export SGLANG_DFLASH_COLUMN_PARALLEL_FC=1

# Add to the section 1 command (replacing its batch settings):
    --max-running-requests 1 \
    --torch-compile-max-bs 1 \
    --tpu-compile-bs 1 \
    --speculative-algorithm DFLASH \
    --speculative-draft-model-path RadixArk/Kimi-K3.1-Dflash2-Preview \
    --speculative-num-draft-tokens 8 \
    --speculative-draft-attention-backend pallas_tpu_rpa_v3 \
    --speculative-draft-kv-cache-dtype bf16
```

`SGLANG_DFLASH_COLUMN_PARALLEL_FC` shards the draft's context projection over
TP (column-parallel, gathered output).

## 3. Image input

The section 1 server is text only. For image input, generate the command from
`benchmark/tpu/recipe/configs/kimi_k3_1/server_vl.py`: the section 1 command with
`SGLANG_TPU_VL_TEXT_ONLY_EXTEND=0` (it also compiles the image prefill graphs),
`SGLANG_TPU_ENABLE_VISION_SPLASH_ATTENTION=1`, and at most 32 running requests
(`--max-running-requests 32 --torch-compile-max-bs 32 --tpu-compile-bs 1 2 4 8 16 32`).
The Kimi-K3 processor admits images of up to 65536 patches; the default vision
attention does not compile above about 16K patches, while splash attention
precompiles the vision encoder up to 66564 patches.

Measured on 16 chips with `reasoning_effort` max: OCRBench **0.874** (all 1000)
and MMMU-Pro (standard, 10 options) **0.860** on a 50-question subset. Startup
takes about 37 minutes, and free host memory drops to about 160 GB per host
while it compiles.

## 4. Measured performance

Four tpu7x hosts (16 chips), all 93 layers, the native server (section 1) without
speculative decoding unless stated.

Measured in November 2026 on four tpu7x hosts (16 chips), all 93 layers.

Single-stream decode (8k in / 1k out; the megakernel rows use short prompts):

| Configuration | TPOT | Decode speed |
| --- | --- | --- |
| Native (section 1) | 7.52 ms | **~133 tok/s** |
| Native + DFlash (section 2) | 5.34 ms | **~187 tok/s** |
| Decode megakernel + DFlash (experimental), GSM8K, mean accept length 4.4 | 1.88 ms | **~530 tok/s** |
| Decode megakernel + DFlash (experimental), accept length fixed at 6 | 1.42 ms | **~700 tok/s** |

Long context, one request:

| Context | Decode TPOT | Decode speed | TTFT, 90% prefix-cache hit |
| --- | --- | --- | --- |
| 64K | 8.6 ms | **~116 tok/s** | 2.3 s |
| 128K | 8.9 ms | **~112 tok/s** | 5.1 s |

With the DSA indexer token split, a cold 64K / 128K prompt prefills in 13.5 /
27.0 s (20-29% faster than without it).

Multi-turn / agentic serving (90% prefix-cache hit), within a TPOT p90 of 30 ms:

| Context | Concurrency | TTFT p90 | TPOT p90 | Throughput (input + output) |
| --- | --- | --- | --- | --- |
| 8K | 16 | 5.5 s | 28.5 ms | ~4.7K tok/s |
| 32K | 8 | 7.3 s | 27.6 ms | ~9.0K tok/s |
| 64K | 4 | 7.5 s | 24 ms | ~10.0K tok/s |
| 128K | 2 | 6.4 s | 21.6 ms | ~11.0K tok/s |

The fixed-acceptance row follows the usual speculative-decoding benchmark
convention (`SGLANG_SIMULATE_ACC_LEN=6`): it measures speed at that acceptance
length, not output quality. The decode megakernel runs all 93 decoder layers as
one Pallas call per step (see the Kimi-K3 TPU deployment); for K3.1 it also runs the DSA indexer
inside the kernel. It is experimental and serves one request at a time.
